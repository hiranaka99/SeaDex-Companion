# Runtime ownership

`server/index.ts` composes the server: it builds one route table from the `*-routes.ts` modules, applies the session check, serves static files, and owns startup and shutdown. A route is a method, a path, an access level, and a handler (`server/router.ts`). Handlers answer with `sendJson` and refuse by throwing `HttpError` (`server/http-error.ts`) with the status and any extra body fields; `AuthError`, `PlanRejected`, `OwnershipError`, `DownloadJobConflict`, and `UsenetSelectionError` are subclasses. Anything else that is thrown is logged and answered with HTTP 500. The rules behind a request live with the data they change (`user-rules.ts`, `hidden.ts`, `config-service.ts`), not in the handlers. Production modules and tests import their owners directly; there is no barrel module.

Everything specific to one download client sits behind `DownloadClientAdapter` (`server/download-client-types.ts`), implemented by `qbittorrent-adapter.ts` and `sabnzbd-adapter.ts` and handed out per protocol by `downloadClients(config)`. Request handlers (`download-routes.ts`) and the scheduler (`scheduler.ts`) hand those clients into review (`download-preflight.ts`), submission (`download-submit.ts`), progress and control (`download-progress.ts`), and free-space checks (`download-space.ts`), which walk the adapters and do not branch on protocol. Each adapter plans its own download units from the rows review hands it (`torrent-units.ts`, `usenet-units.ts`): a unit's client-only fields sit under `send`, typed per protocol, and only that adapter reads them. Review keeps row validation, blocks, ownership, contested sources and disk checks. A new client means a new adapter. `planDownloads` is pure planning; `buildDownloadPlan` additionally stores the expiring plan a review is confirmed with, so accepting a plan re-plans without storing another one.

Usenet indexers are described once in `server/usenet-providers.ts` (label, settings keys, lookup, NZB fetch, connection test, entry-ID shape); the resolver, cache validation, settings invalidation, and connection tests read that registry. Request pacing, priorities, and channel pauses belong to `LookupScheduler` (`server/usenet-scheduler.ts`). Callers hand it a job through `schedule` and never hold a slot themselves: the scheduler takes the slot, runs the request under its wall-clock guard and cancellation, records the outcome for the channel, and frees the slot whether the request answered, failed, timed out, or was cancelled. A queued background job is promoted through the handle `schedule` returns. Pacing is fixed when a scheduler is created. It has two instances that share nothing: `usenetScheduler` in `usenet.ts` serves the hash indexers, one channel per provider ID, and `searchScheduler` in `usenet-search.ts` serves Prowlarr's Usenet indexers, one channel `prowlarr:<indexer id>` per indexer, created on first use. A slow indexer search therefore never takes a slot from a hash lookup. Both sides keep their running lookups in a `FlightTable` (`server/lookup-flights.ts`): a lookup already running for the same key is joined, a caller that is not background promotes it and every request it waits on, and a `LookupEpoch` that the owner invalidates when the connection changes cancels every lookup of the tables sharing it and marks what they learn afterwards as discarded. The same module holds the wall-clock guard the scheduler races against cancellation (`guarded`, `LookupGuardTimeout`) and the `WarningThrottle` that writes a repeated failure warning once a minute per subject. The Prowlarr file-list search is described under [Usenet finder through Prowlarr](#usenet-finder-through-prowlarr).

Identities and guards used on both sides of the API are defined once under `shared/`: `ids.ts` (info hashes, review-row keys, season tags, card keys), `guards.ts`, and `errors.ts`.

The scan service resolves its dependencies once. Its coordinator owns admission, cancellation, progress, commits, and notifications; `assessment.ts` computes a season recommendation without I/O. Sonarr and Radarr adapters load independently. Shared API contracts describe results and configuration, while `result-model.ts` normalizes old cached results before they reach API readers or download commands.

`shared/download-plan.ts` owns upgrade eligibility, torrent hash normalization, and per-hash file selection. Review, estimation, and execution consume those rules. Whole-torrent requests override scoped requests; file scopes are united across selections. Incomplete metadata stays uncertain and never becomes permission to download unrelated files.

Recommendations are identified by result/release identity. Acquisitions are identified by app-owned record ID and bound client endpoint, with source hashes, effective file scope, and every library/release association retained separately. Frontend projection validates the current hashes and scope before attaching a record to a recommendation. A replacement recommendation cannot change the acquisition selected for control or cancellation.

Download jobs capture each unit's actual selection associations before external work. `POST /api/download-jobs` returns an accepted job ID; `GET /api/download-jobs/:id` and `/latest` expose persisted state. Unfinished jobs become interrupted on restart rather than repeating side effects. Every admitted job reaches a terminal outcome when its state can be persisted, including ownership-intent failures. Single-release receipts aggregate every required source, and row outcomes stay pending until all sources settle. One frontend observer handles submission and reload recovery, and the retained download store survives card pagination and unmounts. `frontend/src/bulk-operation.ts` turns that observer's job into the operation banner, one projection for live batches and reloads, and owns dismissal, the review of the batch started in the session, and the cancellation outcome; the sidebar, the mobile banner, and the library read it through `useBulkOperation`. The frontend `api.ts` reports a single-release send as a `SendOutcome` (sent, rejected with a reason, or acceptance unknown with the client named); callers never read the receipt or the error body themselves. Display helpers for owned downloads that hooks need live in `download-entry.ts`, not in a component module.

qBittorrent sessions and caches belong to each connection. Mutation locks belong to torrent hashes; sorted acquisition prevents multi-hash deadlocks. Metadata loading therefore does not block independent status reads or controls.

## Provider discovery and reviewed plans

Each scheduler instance assigns capacity only when a channel's pacing permits a request to start. Foreground requests precede queued background work, and background work never holds the reserved slot: the hash scheduler has four slots and the Prowlarr scheduler three, each with one reserved for foreground work. Every channel starts at a 2-second minimum interval. Spacing adapts per channel: a `rate_limited` outcome multiplies the current interval by 1.5, up to 15 seconds (concurrent failures widen it once); every 20 consecutive answers take 10% off, and a channel narrowed to its minimum follows the minimum again. Any failure restarts the count of answers. The adaptive interval lives in memory only, so a restart starts every channel at its minimum. Rate limiting, or three consecutive transient failures, pauses that channel for all requests (30 seconds doubling to 10 minutes, or longer when `Retry-After` asks). Queued foreground lookups fail fast with the pause reason while other channels keep answering. Background lookups wait out the pause and retry. A Prowlarr indexer whose `status.disabledTill` lies in the future pauses its channel until then; the pause ends early once Prowlarr stops reporting it, unless failures of Companion's own requests extended it. `usenetProviderPauses()` reports the pauses of both instances with each channel's label, which the sidebar and operation center show. Only changes to provider URLs, keys, or enablement invalidate in-flight work, and results are discarded only for that invalidation epoch. A general configuration generation bump does not cancel lookups. Each prefetch sweep owns an epoch; superseded work cannot overwrite current progress. Sweeps order results by likely download (missing and partial, then upgrades, then owned best releases), check best releases before alternatives, and skip excluded seasons and parts.

Availability requests validate canonical release identities before querying providers. Internal resolvers retain complete validated manifests for scope decisions. The public availability projection bounds filename lists and clears their completeness flag when names are omitted. NZB validation reads the standard nested segment structure and accepts the standard public declaration without resolving external entities. `server/usenet-provider-types.ts` holds the two steps every Usenet indexer request goes through, and their types; each client keeps only how it builds its request URLs and reads its items. Every Newznab search, an AmeNZB hash search or a search of one of Prowlarr's indexers, goes through `searchNewznab`: one GET on the configured origin without redirects, its status, a capped read, the XML, an error document (never an empty answer, whatever status it arrives with) and the feed items. It returns the items or a `NewznabFailure`: a failure code, safe text, `Retry-After` when given, and a scope (`indexer` or `prowlarr`, see [Usenet finder through Prowlarr](#usenet-finder-through-prowlarr)). Newznab error codes are read once, by `newznabErrorFailure`, for searches, NZB fetches and Prowlarr downloads alike. Every NZB fetch, from AnimeTosho, AmeNZB or a Prowlarr grab, goes through one step, `readNzb`: it applies the 16 MiB cap to the body as sent and once decompressed, inflates a file-compressed NZB once, rejects a Newznab error document and validates what is left. It returns the NZB or a typed failure that each client turns into its own error. The steps are built from bounded HTTP to a provider origin (`server/provider-http.ts`) and Newznab and NZB XML reading (`server/newznab-xml.ts`), which AnimeTosho's JSON lookup and Prowlarr's own API also use.

`server/usenet-cache.ts` owns `DATA_DIR/usenet_cache.json`, a versioned cache of provider observations. Records are scoped by provider, source hash, and a SHA-256 fingerprint of the provider URL and credentials. The file stores neither those credentials nor credential-bearing URLs or NZB payloads. Cache reads do not rewrite the file, and incompatible provider configuration removes only the affected records. Each sweep, including one that does not run because the configuration is ineligible, prunes records for source hashes that the current results no longer reference. A 20,000-record bound remains only as a safety limit; age alone does not delete an observation.

Freshness intervals are 7 days for a usable source and 10 minutes for processing. For no match or deletion they grow with consecutive absences: 1 hour, 6 hours, 1 day, then 7 days. A match resets that count. Lookup failures retry after one minute, or after the provider pause if that is longer. An AnimeTosho entry without an NZB counts as processing only while its status is `processing` or it is under 48 hours old (or has no timestamp). Older entries are reported as no match, because AnimeTosho marks never-mirrored releases with status `unknown` indefinitely. AnimeTosho lookups use a 16 MiB response cap, because their per-file hashes and media info reach about 45 KB per file. AmeNZB lookups and capability probes keep the 512 KiB cap. Public availability returns cached or unchecked snapshots immediately and coalesces missing or stale checks in the background. Failed refreshes retain prior observations with retry state and an error. Observation timestamps reflect provider work, not cache access. Open reviews observe only their refreshing rows and retain cached data and choices until updated results arrive.

Successful provider observations are appended to `DATA_DIR/usenet_cache.journal.jsonl` before exposure, including on platforms that can terminate a process without shutdown hooks. The snapshot is rewritten atomically at most every 30 seconds and on graceful shutdown, and each rewrite removes the journal it absorbed. On load, journal records replay over the snapshot unless the snapshot record is newer, and a torn final line is skipped. If the append fails, the snapshot is written immediately instead. Failure metadata and pruning use the same batched snapshot writes. Authoritative resolver and preflight calls await fresh-on-stale data rather than treating retained stale observations as a new successful check. For AnimeTosho and AmeNZB, the actual provider NZB is fetched and validated before SABnzbd submission. An NZB found through Prowlarr is sent from the NZB store instead, as it was checked (see [Persistence and compatibility](#persistence-and-compatibility)).


Bulk review retains its selected result snapshot. Acceptance checks current identities, client presence, and acknowledgements again before writing intents. Provider-backed reviews are cancellable and rely on bounded provider requests rather than a fixed aggregate frontend deadline. Expired or consumed single plans require an explicit fresh review with acknowledgements reset.

## Usenet finder through Prowlarr

`server/usenet-search.ts` finds a Usenet copy of a source the hash indexers cannot provide: a private-tracker release (`files:<sha1>`), or a public info hash that every enabled hash indexer answered "no NZB" for and whose files SeaDex lists (`fileListSources` in `usenet-copies.ts`). A failed or still-processing hash lookup never qualifies. The finder has two stages. The **search stage** (`searchSource`) sends one Newznab request per indexer and query (`searchIndexer` in `prowlarr.ts`: `GET /{id}/api?t=search&extended=1&limit=100`, key in `X-Api-Key`, 45-second timeout) and merges what it finds into the stored record; it costs no grab and may run in the background. The **verify stage** (`verifySource`) fetches candidates' NZBs through `prowlarrGrabNzb`, grades them with `gradeNzb` (`source-files.ts`), stores the bytes and writes each check at once. `resolveSource` runs both for one caller. A search or check already running for a source is shared, and a foreground caller promotes a background search. Search terms and ranking (`usenet-search-terms.ts`) and the state of a record (`usenet-search-state.ts`) are pure; `usenet-search-store.ts` owns persistence. `private-sources.ts` keeps only the private torrent lookup, which is unchanged.

Prowlarr failures carry a `scope`. `indexer` (429 with `Retry-After`, 410, 5xx, timeouts, a Newznab error document, any failure after a download redirect) affects that indexer only: it is recorded as not answered, its channel learns the outcome, and the other indexers go on. `prowlarr` (a refused Prowlarr key, an unreachable Prowlarr) fails the whole lookup, writes nothing, and is remembered in memory until its retry time. Newznab codes 500 (request limit) and 501 (download limit reached) are read as `rate_limited`, for the hash indexers too. Error descriptions from an indexer are never copied into a message.

**Search ladder.** The common tokens of a source are the tokens (lower case, diacritics removed, split at every non-letter, non-digit) present in every main video file name; files in folders named like extras are left out. Every search title (`searchTitles`) is cleaned and ordered with the titles whose tokens are all common tokens first. Each indexer gets at most four queries per source: A, the group and the first title; B, the first title alone with `minsize` and `maxsize` of 0.97 to 1.35 times the listed total; then the group with the second and the third title. A comes before B when the group's tokens are common tokens, B first otherwise. Without a group the queries are up to three sized titles; without a title, the sized group. No query names a category. A query goes to every active indexer at once, and the ladder stops after the first query that yields a strong candidate that is not already graded or rejected. A result is plausible when its size is unknown or 0.97 to 1.35 times the listed total, and its title names the group as whole tokens (the group's tokens in a row, or the group without punctuation equal to one token or up to three adjacent tokens joined) or carries at least 60% of the common tokens. A strong candidate is plausible with a known size of 1.0 to 1.25 times the total. Candidates rank by group match, name coverage, closeness to 1.08 times the total, then a reported file count that can hold every listed file, then a non-zero grab count; the file count never rejects. A record keeps 20 unchecked candidates at most and never drops a checked or rejected one.

**Proof levels.** `nzbFiles` returns every `<file>` of a validated NZB with the name and size its subject states (an unparsable subject gives an empty name) and the sum of its `<segment bytes>`. The ratio of a file is its segment bytes divided by its listed size. `gradeNzb` returns the first level that holds; the thresholds are named constants beside it.

| Level | Rule | Sent |
| --- | --- | --- |
| `exact` | Every listed video file appears with its base name and exact size in a subject (`nzbHasFiles`) | Automatically |
| `near_exact` | Every video file's base name appears, each ratio is within 1.005 to 1.06, and the ratios of video files of 64 MiB or more differ by at most 0.005 | Automatically, labelled near-exact |
| `probable` | At least three video files, and one ratio within 1.005 to 1.06, fixed by a partner of the largest video (at most 64 trials), gives every listed video size its own NZB file within 0.005 | Only when chosen and confirmed |
| `size_only` | All segment bytes divided by the total of all listed files is within 1.005 to 1.35 | Only when chosen and confirmed |
| `unverified` | None of these | Only when chosen and confirmed, with a warning that the sizes differ |

A row names a chosen candidate by its entry ID (`nzb`); only a candidate that was fetched, graded and not rejected can be chosen, and only for the Usenet protocol. Every graded NZB is logged at INFO with its indexer, proof and lowest and highest ratio, so the ratios of exact matches can confirm the accepted range on the installation's own indexers.

**The Usenet copy resolver.** `server/usenet-copies.ts` is the one place that decides where a Usenet copy of a release can come from: the hash indexers by torrent hash, the Prowlarr fallback for a hash they all lack, or Prowlarr alone for a private-tracker release. Availability (`usenetAvailability`), download review and acceptance (`planDownloads`), and the background sweep ask it through `resolveUsenetCopies`, one request per release with a named **intent**, and never combine hash lookups, fallback sources, search terms and Prowlarr results themselves. Its answer per release is the rows, their aggregate, whether Prowlarr found or may be searched for a copy, and the file-list sources a copy is checked against. `cancelCopyChecks` withdraws what `check` rows started, and `searchInBackground` is the sweep's search stage. Only the availability intents read Prowlarr's indexer list to report a private-tracker source as `not_configured`, because reading it may refresh it and a review or an acceptance never asks Prowlarr about such a release.

**What each caller may spend.** A fetch counts as a grab on the indexer, so it runs only for a user action. The resolver holds this table as the budget of each intent:

| Caller (intent) | Searches | NZB fetches |
| --- | --- | --- |
| **Search Prowlarr** and **Search again** (availability `search` rows; `search`) | Always, every indexer | Up to 3, also when the source is `no_match` or `lookup_failed` |
| A single download review (`buildDownloadPlan` with one selection; `single_review`) | Only without a fresh record | Up to 3, only while the source is `unverified` |
| **Check now** in release details and a bulk-review row (availability `verify` rows; `check`) | Only without a fresh record | 1, only while the source is `not_checked` or `unverified` |
| Any other availability row (`look`) | Never | Never |
| Bulk review preflight (more than one selection; `bulk_review`) | Never | Never |
| Acceptance of any plan (`acceptance`) | Never | Never |
| Background sweep (`sweep`, then `searchInBackground`) | Only when stale, counted | Never |
| Submission (not a lookup; `searchNzbBytes`) | Never | None, unless the stored bytes were evicted |

A walk stops at the first `exact` or `near_exact` candidate or at its limit. A candidate whose indexer is paused or out of fetches is skipped without an error, and the row carries the reason ("Daily NZB check limit reached for <indexer>. Next check at <time>."). An indexer-scope fetch failure marks the candidate `unavailable` until a retry time (at least a minute, `Retry-After` and the channel pause respected) and stops fetches from that indexer for the walk; the source is then `lookup_failed`, never `no_match`, unless another candidate is proven. An `invalid_response`, whoever reported it, is the candidate's own fault: it is not fetched again for 7 days and the walk goes on. Any other Prowlarr-scope failure ends the walk. A bulk review sends its `verify` rows as `cancellable`; `cancelSourceCheck` (`cancel_verify` rows) drops a check still waiting for its slot, and a fetch already under way finishes and is stored.

**Freshness** (`searchRecordState`):

| Stored result | State | Fresh for |
| --- | --- | --- |
| A candidate proven (`exact`, `near_exact`) and not rejected | `available`, with `proof` | 30 days |
| A candidate whose fetch failed and may not be retried yet, none proven | `lookup_failed`, naming the indexer | 7 days; the candidate counts as unchecked again at its retry time |
| Candidates graded or rejected, none proven | `no_match`, with the candidates | 7 days |
| Candidates, none checked | `unverified` | 7 days |
| No candidate, an indexer did not answer | `lookup_failed` | Until its retry time, at least one minute |
| No candidate, every indexer answered | `no_match` | 1, 3, 7, then 30 days on consecutive absences |
| No record | `not_checked` | |

Freshness counts from the later of the search and the latest grading. A record is also stale when an enabled indexer is missing from it, or is listed as not answered and its retry time passed; the refresh asks only those indexers and merges their candidates. Only a search of every indexer renews `searched_at`. `aggregateHashStates` ranks `unverified` after `processing` and before `not_checked`. Availability (`usenetAvailability`) reads the store and never waits on Prowlarr; rows report `refreshing` while a search or check runs, and the response carries `prowlarr_usage` (fetches left and pauses per indexer).

**Usage counters and limits.** The store counts searches and fetches per Prowlarr fingerprint and indexer in hourly buckets; an hour leaves the window 24 hours after it ends. Only background searches are counted, read with the slot in hand; their limit is `prowlarr_search_limit`, or half of the indexer's own query limit in Prowlarr when that is lower, and with `prowlarr_search_limit` at 0 that half alone. Every NZB fetch is counted, including a re-fetch for a submission, and the count is written before the request is sent; the limit is `prowlarr_fetch_limit`. 0 means no limit from Companion. Prowlarr's limits are read from `baseSettings.queryLimit`, `grabLimit` and `limitsUnit` (Day = 0, Hour = 1 assumed from Prowlarr's source; an hourly figure counts 24 times). The grab limit is read but does not cap fetches; Prowlarr's own 429 pauses the channel. Changing the search limit, the background toggle or the tracker mode restarts the sweep; a changed fetch limit applies to the next fetch. Neither invalidates anything.

**Background search sweep.** `usenet-prefetch.ts` runs the search stage after the hash sweep, when `prowlarr_background_search` is on, SABnzbd is configured, the download mode is not **Torrents only**, Prowlarr is enabled, and its indexer list, read once per sweep, has a Usenet indexer. It needs no hash indexer. It walks the sources of the `prefetchPlan` order that qualify (private-tracker sources, and hashes the sweep found `no_match`), skips fresh or running ones, searches each at background priority, and stops early when every indexer has spent its searches. It never fetches. Progress is `usenet_prefetch.search` in `/api/status`. A finished stage stores and logs a summary (searched, with candidates, without, failed, deferred, queries per indexer), which `GET /api/prowlarr/search-status` returns with the expected searches for the current results; a superseded sweep stores nothing.

**Outcome feedback.** `settleImports` (`import-follow.ts`) runs with every new set of results. A ledger record with `provider: 'prowlarr'` and a `proof` other than `exact` is a mismatch when, for one of its library targets, the result lists the target's group in `mismatched_by_part`, the library does not hold the release, and the part's library size differs from `local_size`, the size recorded when the download was sent. That size guard keeps an unrelated earlier release of the same group, or a result a scan of other titles left unchanged, from counting. Records sent before this change have no `local_size` (and no `proof`) and are never judged. A mismatch rejects the candidate (`rejectSearchCandidate`, written at once), sets the import state `mismatch` with "The downloaded files are not the release SeaDex lists; their sizes differ.", and is reported once through the import-problem notification. A mismatch is final. A rejected candidate is never ranked, checked or reported as available again; its source becomes `no_match` with its candidates, so **Search again** can try another. Detection needs `mismatched_by_part`, so it does nothing while **Check owned releases by file size** is off. If the rejection throws, the record is left for the next scan.

## Library instances and scope

`server/arr-instances.ts` presents the first Sonarr and Radarr (saved in their dedicated settings) and every additional instance (`arr_instances`) as one list. The first instance of each kind keeps the bare application name as its key prefix, so existing library keys (`Sonarr:item10`), result keys, user rules, and hidden-card keys stay valid. An additional instance prefixes them with its immutable identifier (`Sonarr@<id>:item10`, card key `<id>:<group>`), and its results carry `instance` and `instance_name`. Scan errors are keyed by instance name, which is why names are unique and cannot be `Sonarr` or `Radarr`. Download categories are resolved from the instance of the result, never from the application kind alone.

API keys of additional instances live in the same encrypted payload as the other credentials, under `arr_instance_keys`. The public configuration returns each instance with an empty key and a `key_configured` flag; a blank key in an update keeps the stored one.

A library scope is applied while loading an instance, before any per-title request. Tag labels are resolved to IDs once per load; a scope whose tags cannot be read fails that source rather than scanning everything. Titles outside the scope are returned separately with their tags, only so stale status tags can be removed from them.

## Assessment settings

`assessSeason` receives the release preferences and the file-check switch. Preferences choose the download target (`pickBest`) and decide which owned releases settle a part; they never remove a release from the result. Each listed release keeps SeaDex's own `kind` and may carry `target`, `excluded_by`, and `satisfies` (stored only where it departs from the kind, which is what results saved earlier imply). `shared/download-plan.ts` remains the single eligibility policy: `releaseOwned`, `releaseSatisfies`, `releaseOffered`, and `upgradeParts` are used by the scan, preflight, bulk review, tags, and the interface alike. A part whose releases are all excluded and which the library does not already settle reports `uncovered` with `preference_blocked`, while its releases stay listed for an explicit single download.

File verification (`server/verification.ts`) compares exact library file sizes (`LocalSeason.files`) with the video files a release lists. A match proves ownership whatever the files are named (`verified_by_part`); a release group named in the library whose files differ is recorded in `mismatched_by_part`, and `releaseOwned` then denies ownership. A group's best-flagged uploads are compared separately from its other uploads. Nothing is concluded when either side has no sizes.

Saved results record the signatures of the settings they were computed under. A full scan stores new signatures; a scan of single titles keeps the saved ones, because the other results were not re-judged. When the assessment signature differs from the saved one, the scan is a baseline: it records no unseen release changes, restores no hidden titles, and reports no regressions. `/api/status` exposes `settings_changed` from these signatures, cached per results revision and configuration generation.

The tracker mode `reachable` (**Include private trackers Prowlarr can reach**) lists every release, as `private` does. `AssessmentSettings.coveredTrackers` names the private trackers Prowlarr has an enabled private torrent indexer for (`trackerIndexers`), read once at the start of a scan (a scan of single titles accepts the cached indexer list); `assessSeason` asks nobody. When a part's chosen target is a private-tracker release on a tracker not covered, the target becomes `pickBest` over every eligible candidate that can be fetched, public ones and those on a covered tracker alike: a best-flagged one, or an alternative when none is flagged. The part is judged against that target, which settles the part when owned even if it is only an alternative. The release that gave way keeps its own `kind`, is never the target, and carries `excluded_by` "On <tracker>, which Prowlarr cannot reach", which keeps it out of bulk downloads like a preference exclusion; an explicit download from release details still works where it can be fetched. When the replacement is the same release on a covered tracker, the two are one listing and no note is added. When nothing else can be fetched, the target stays. Without Prowlarr enabled, no tracker counts as covered. `privateSearchSettings` treats `reachable` as `private`.

The `private` and `public` signatures are unchanged: `private` adds nothing to the preferences and file-check switch, and `public` appends `'public'`. `reachable` appends `'reachable'` and the sorted, lower-cased covered trackers, so a change of coverage makes the next full scan a baseline. When Prowlarr's indexer list cannot be read, the scan logs a warning and reuses the covered trackers of the saved signature (none when the saved signature is not a reachable one). `resultSettingsChanged` cannot read Prowlarr, so it compares against the saved signature's own coverage, and a coverage change alone never shows the settings-changed notice. The note travels in `excluded_by`; there is no separate field.

A regression (`describeRegression`) is a season that was best and is now upgradable while the catalog facts are unchanged apart from notes and the library's groups or size changed. It is recorded as its own scan-history type, as an unseen change of kind `regression`, and replaces the wording of the upgrade notification for that season.

## Import follow-through and status tags

Records in `owned_downloads.json` created with known library seasons carry `library` targets and an `import` state. `setDownloadPhase` moves `waiting` to `pending` on the first sight of a finished download, whoever read the client. The scheduler runs `followImports` once a minute while any record needs it: it reads the download clients, reads each involved instance's queue once, and matches entries by download ID. A queue entry with a problem becomes `blocked` with the app's messages. A download absent from the queue after a two-minute grace period triggers a rescan of its title (trigger `import`); after twenty minutes, one more rescan, and then `not_imported`. Only `settleImports`, called with every new set of scan results, confirms an import, by `releaseOwned` on the season the download was sent for. It also settles an unproven Prowlarr NZB whose files arrived with other sizes as `mismatch` (see [Usenet finder through Prowlarr](#usenet-finder-through-prowlarr)); the follower reports it once like `not_imported`. The follower never writes to Sonarr, Radarr, or a download client. Queue read failures back off for five minutes per instance.

Import webhook events are accepted only for titles already present in the results; add events are always accepted. Scans of single titles reuse a catalog loaded within the last fifteen minutes.

`server/arr-tags.ts` is the only code that writes to Sonarr or Radarr, and only when `arr_tags_enabled` is set. After a scan it derives one state per title, compares it with the tag IDs loaded during that scan, and uses the series or movie editor endpoints to add or remove only the configured tags. Tag definitions are created on first use. Failures are logged and never fail the scan.

## In-app updates

The image starts `dist/server/launcher.js`, not the server. The launcher runs the app built into the image or, when `DATA_DIR/app-updates/active.json` names a bundle that is newer than the image and carries the same `runtime.json`, that bundle's `dist/server/index.js`. A bundle holds `package.json`, `runtime.json`, `dist/server`, `dist/shared`, and `static`; it has no packages of its own and resolves the image's through a `node_modules` link the launcher creates. The launcher sets `DATA_DIR`, `SEADEX_LAUNCHER=1`, `SEADEX_IMAGE_ROOT`, and, for a bundle, `STATIC_DIR`. On start it deletes the pointer when its bundle cannot run on this image (older or equal version, missing files, other runtime) and removes every bundle directory other than the active one and its `previous`.

`runtime.json` is the `RuntimeIdentity` from `server/runtime-identity.ts`: the Node.js major, a hash of the `Dockerfile` and entrypoint, a hash of `server/launcher.ts`, and every production package version from `package-lock.json`. The image computes it during the build, and the release workflow computes the same value for the bundle. Any difference means the release needs a new image, and `runtimeDifferences` turns the difference into the reasons the update dialog shows. The launcher must import only Node built-ins, because only its own source is hashed.

`server/updates.ts` reads the latest GitHub release, the `seadex-companion-update.json` manifest asset, and decides `in_app`, `image_required` (incompatible runtime or no manifest), or `unavailable` (not under the launcher, or an unreadable or invalid manifest). `POST /api/update/install` refuses during a scan or an unfinished download job, downloads the bundle named by the manifest (64 MiB limit), checks its size and SHA-256, unpacks it with the regular-files-only reader in `server/tar.ts`, verifies its version and runtime, stages it, and writes `active.json` with `pending: true`. After the response it asks `server/lifecycle.ts` for a restart: the server shuts down gracefully and exits with code 75, and the launcher starts the new copy.

The server sends `seadex:ready` over IPC once it listens; the launcher then clears `pending`. A pending bundle that exits before that message is rolled back: the launcher returns to `previous` (or the image's app), deletes the failed bundle, and records `last-failure.json`, which `/api/update-check` and `/api/update/status` report while the failed version is newer than the running one. A bundle that started once is never rolled back automatically. Exit code 75 more than five times in a minute stops the launcher.

# Persistence and compatibility

AniList metadata is persisted under `media:v1:<id>` and shared by automatic chains and explicit season matches. Known IDs from the active scan's saved title matches, chains, and manual selections are loaded through `Page.media(id_in: ...)` in batches of up to 50, the most AniList returns per page. All batches use the same serialized transport and 2.1-second pacing as interactive searches. Batch errors must propagate rather than being cached as missing titles; successfully omitted IDs are cached as missing for 24 hours.

`saveCache` marks `anilist_cache.json` for saving instead of writing it: a scan saves after every title and every batch, and the file is several megabytes. `flushCache` writes it at most every 30 seconds, when a scan ends (finished, failed, or cancelled), and on graceful shutdown. Metadata that a killed process had not written yet is requested again by the next scan. Clearing scanned data discards unsaved metadata.

Raw metadata and derived season/chain caches expire after 24 hours. Derived caches inherit the oldest raw metadata timestamp used, preventing reuse from extending stale metadata indefinitely. A newly required Sonarr season forces one relation refresh even for fresh raw data. Fully manual items skip automatic title matching and traversal, and use manual metadata for continuous episode offsets only when inferred matches agree with every explicit selection.

Configuration settings and their AES-GCM encrypted credentials share one atomic `config.json` commit. Ordinary reads do not write. `loadConfig` keeps the parsed and decrypted configuration until `config.json`, the key file, or the legacy secrets file changes (inode, modification and change time, size), and `saveConfig` drops it at once. Every caller receives its own copy. Startup migration reads the former separate secrets file without replacing the existing key. Back up the complete data directory before upgrading; restore that backup for older versions that expect separate credential storage.

`owned_downloads.json` contains the versioned protocol-neutral record ledger and its release associations. Legacy ownership arrays, versioned torrent dictionaries, and separate `download_records.json` details are read together during migration. Ownership, scope, native-ID bindings, and associations are committed before publishing in-memory state. Failed writes leave the prior ledger intact. A record's source is a BitTorrent v1 info hash, except for a Usenet copy of a private-tracker release, which uses that release's `files:<sha1>` file-list identity. Torrent records always keep a real info hash and may carry the file-list identity as `source_alias` (see section 16 of the [Usenet plan](usenet-implementation-plan.md)). A record sent from an NZB found through Prowlarr carries the `proof` of that NZB, and each library target the part's library size when the download was sent (`local_size`). Both are optional: records without them load unchanged, and an unknown proof value is dropped.

`server/usenet-search-store.ts` owns `DATA_DIR/usenet_search.json` (version 1, mode `0600`, written with `writeJsonAtomic`): one search record per Prowlarr fingerprint and source, the hourly usage counters, and the latest sweep summary with the fingerprint it belongs to. A candidate's download reference is only the `link` and `file` parameters of Prowlarr's download link; the path is rebuilt in memory with the configured key for each fetch, and a stored value that looks like it carries a key is refused. `link` is Prowlarr's encrypted form of the indexer's address and never reaches the browser or a log. The file is read on first use and validated field by field; invalid records and entries are dropped with a warning, and no parser message is logged, because it could quote part of a link. Search-only updates and search counters are batched: written at most every 30 seconds (a failed write retries after a minute) and by `flushUsenetSearch` on graceful shutdown, beside `flushUsenetCache`; a failed flush makes the process exit with code 1. A check, a rejection (`put` with `durable`), a counted fetch (`countFetch`, before the request is sent) and a removal of another connection's data are written before the call returns, so a fetch is never spent twice after a crash.

Fetched NZBs live in `DATA_DIR/nzb_store/<sha256>.nzb.gz` (directory `0700`, files `0600`), gzipped and named by the SHA-256 of the uncompressed bytes, written beside their final name and renamed. Every graded NZB is stored, proven or not, so a candidate chosen later costs no second fetch. A read checks the hash and removes a file that fails; leftover temporary files are removed. A file no candidate names is removed after a 10-minute grace. Above the 256 MB budget, NZBs go oldest first by the latest check that names them, but one checked in the last 24 hours goes only above the 512 MB hard limit. An evicted candidate keeps its check; submission (`searchNzbBytes`) then fetches it once more within the fetch limit and sends it only when it has the same SHA-256 or grades to the same proof against the source's file list. Otherwise the check is replaced, or dropped when nothing can be compared, and the review has to be run again.

`invalidateUsenetSearch` runs at startup and whenever `prowlarr_enabled`, `prowlarr_url` or `prowlarr_key` changes. It cancels running searches and checks, discards their results, resets the Prowlarr channels (another Prowlarr numbers its indexers the same way), and keeps the records, counters, summary and NZBs of the configured URL and key only; everything goes when none is configured. Turning Prowlarr off alone therefore keeps its results. Each sweep start, including one that does not run, prunes records, with the NZBs only they name, whose source is neither a hash or private source of the current results nor the `source_hash` or `source_alias` of an active ledger record. A record is active until it is removed or settled: settled means imported when its import is followed, and finished in its client (`complete` or `seeding`) when it is not. When the ledger cannot be read, nothing is pruned. Earlier versions held Prowlarr results in memory only, so there is nothing to migrate.

`loadLastResults` keeps the parsed and normalized results file until its inode, modification time, or size changes, and saving or clearing results drops it at once. Like the scan state's results, the value it returns is shared, so readers must not modify it. A running scan normalizes each title's seasons once and publishes the growing snapshot with `setNormalizedResults`. The browser reloads that snapshot at most every 10 seconds while a scan runs, and once more when it ends. `loadResultSettings` keeps the settings signatures and result count per version of the results file, and saving results sets them without reading the file back. A scan matches its results to the previous ones through one index built by `previousResultMatcher`. Sonarr episodes are requested for four series at a time, and the library keeps Sonarr's order. Progress reads of up to 100 torrents ask qBittorrent for those hashes only.

## Responses and polling

`sendJson` compresses bodies of 1 KiB or more with Brotli or gzip, whichever the request's `Accept-Encoding` prefers, off the main thread; smaller bodies are sent as they are. `server/static-files.ts` serves text assets and the TTF font compressed, keeps each compressed copy in memory per file version, and compresses the files under `assets/` once at startup. Hashed files under `assets/` are immutable. Every other file carries `Cache-Control: no-cache` and a weak `ETag` from its size and modification time, so a reload revalidates it with a 304 instead of downloading it again and a new deploy is still picked up at once.

The History, Configuration, and Log pages are separate chunks loaded on first use and fetched ahead of time while the browser is idle. A chunk that cannot be fetched, for example in a tab left open across an update, shows the page error with a reload action.

The status, download-progress, and log polls read nothing while the tab is hidden and read at once when it is shown again. The download store keeps its snapshot object when an answer repeats the previous one, so cards re-render only when a download changed.

Job updates also write before publishing in-memory state. Readers receive copies, and no credentials are stored with jobs. Unknown acceptance retains duplicate protection. A fresh complete client read can establish presence or absence; malformed, failed, or endpoint-mismatched reads cannot. Removal of a confirmed missing acquisition changes only tracking and preserves files.
